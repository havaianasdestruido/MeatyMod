# Phase 0 — Reverse Engineering & Research (MANDATORY)

Before writing **any code**, thoroughly study the target game to understand its architecture. Do **not** begin implementing the modding tool until this research phase is complete.

Your objective is to become an expert on how the game stores, loads, and references its assets so the resulting tool is accurate rather than based on assumptions.

## Research Goals

Analyze every executable, DLL, and data file included with the game.

Examples:

* Game executable(s)
* .NET assemblies
* Native DLLs
* Engine libraries
* Plugin libraries
* Asset archives
* Configuration files
* Manifest files

Determine:

* Which game engine is used.
* Which version of the engine is used.
* Whether the executable is managed (.NET/Mono) or native.
* Which third-party libraries are used.
* Which compression libraries are present.
* Which serialization methods are used.
* How assets are loaded.
* How assets are referenced.
* Whether filenames or IDs are used.
* Whether hashes are used.
* Whether encryption is present.
* Whether integrity checks exist.
* Whether assets are loaded synchronously or asynchronously.
* Which folders are actually scanned by the game.
* Which files are ignored.
* How localization works.
* How save files work.
* Whether mods can be loaded without replacing originals.

## Reverse Engineering

Perform static analysis first.

Only infer behavior from observable evidence.

Use techniques such as:

* Assembly inspection
* Metadata analysis
* String extraction
* Resource inspection
* Import/export table analysis
* IL decompilation (if managed)
* Symbol discovery
* Dependency graph generation
* Asset reference tracing

If the executable is managed (.NET), inspect:

* namespaces
* classes
* methods
* resource loaders
* content managers
* serialization classes
* asset pipelines

If native:

* imported APIs
* RTTI
* exported symbols
* embedded resources
* file format parsers

## Asset Pipeline

Document every supported asset type.

For every asset format answer:

* What loads it?
* Where is it loaded?
* Which class loads it?
* Which function loads it?
* Which extension is expected?
* Can it be replaced?
* Is it compressed?
* Is it encrypted?
* Is it cached?
* Is there versioning?

Produce a table like:

| Extension | Purpose | Loader | Importable | Exportable | Compression | Notes |
| --------- | ------- | ------ | ---------- | ---------- | ----------- | ----- |

## Runtime Architecture

Map:

* initialization sequence
* resource loading order
* level loading
* audio loading
* texture loading
* model loading
* shader loading
* localization loading
* save loading

Produce a dependency graph showing how the systems interact.

## File Formats

Reverse engineer every proprietary format.

For each format identify:

* magic bytes
* header structure
* version fields
* offsets
* alignment
* endianness
* compression
* embedded resources
* metadata
* checksums

Document everything.

## Modding Opportunities

Identify:

* safe replacement methods
* asset injection opportunities
* external loading mechanisms
* hidden developer features
* debug flags
* unused content
* console commands
* launch arguments

## Validation

Never assume a file format.

Every conclusion must be backed by evidence found in:

* executable code
* metadata
* strings
* references
* file structure
* observed behavior

If evidence is insufficient, explicitly state that it is unknown instead of guessing.

## Deliverables Before Coding

Before generating a single line of application code, produce:

1. Architecture report. (.ai/report/ARCH.MD)
2. Engine identification. (.ai/report/ENGINE.MD)
3. Dependency analysis. (.ai/report/DEPS.MD)
4. Asset pipeline documentation. (.ai/report/ASSETS.MD)
5. File format documentation. (.ai/report/FILE_FORMAT.MD)
6. Folder structure explanation. (.ai/report/FOLDER_STRUCT.MD)
7. Runtime loading sequence. (.ai/report/RUNTIME.MD)
8. Modding strategy. (.ai/report/MODDING.MD)
9. Risks and limitations. (.ai/report/RISKS_AND_LIMITS.MD)
10. Detailed implementation plan for the modding tool. (.ai/report/IMPLEMENTATION_PLAN.MD)

**Only after this research report is complete and internally consistent should you proceed to implement the modding tool. Every feature of the tool should be justified by the findings from the reverse-engineering phase rather than assumptions.**
