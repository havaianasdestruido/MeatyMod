# Phase 4 — Maintenance, Evolution & Long-Term Support (MANDATORY)

Begin this phase **only after Phases 0, 1, 2, and 3 have been successfully completed and a production-ready release exists.**

This phase governs the continued evolution of the project after release.

The primary objective is to ensure long-term compatibility with future game updates, maintain code quality, resolve defects, improve performance, and safely introduce new functionality without compromising existing behavior.

No change should violate the architecture established in previous phases unless an approved architecture revision is documented.

---

# Objectives

Maintain:

- code quality
- compatibility
- stability
- documentation
- performance
- security
- maintainability
- reproducibility

The application should continue to evolve while preserving backward compatibility whenever practical.

---

# Version Management

Maintain semantic versioning.

Example:

Major.Minor.Patch

Examples:

- 1.0.0
- 1.1.0
- 1.1.4
- 2.0.0

Define:

- breaking changes
- new features
- bug fixes
- hotfixes
- experimental builds
- nightly builds
- release candidates

Every release must include release notes.

---

# Game Update Monitoring

Continuously monitor new game versions.

For every game update:

Determine:

- executable changes
- asset format changes
- archive changes
- serialization changes
- compression changes
- encryption changes
- runtime changes
- loader changes
- localization changes
- save format changes

Perform binary comparisons whenever possible.

Never assume compatibility.

---

# Compatibility Analysis

For every detected game update:

Determine:

- fully compatible
- partially compatible
- incompatible
- unknown

Explain the evidence supporting every conclusion.

Document:

- changed files
- modified structures
- removed assets
- new formats
- deprecated behavior

---

# Regression Analysis

Compare new versions against previous releases.

Identify:

- broken features
- parser failures
- archive failures
- validation failures
- UI regressions
- performance regressions
- plugin compatibility issues

Document every regression.

---

# Completion Criteria

Phase 4 is an ongoing lifecycle rather than a one-time milestone.

The project is considered healthy when:

- New game versions are continuously evaluated.
- Compatibility remains current.
- Critical issues are addressed promptly.
- Documentation remains synchronized.
- Automated tests continue to pass.
- Performance remains stable or improves.
- Security issues are resolved.
- The codebase remains maintainable.
- Every release is fully documented and reproducible.

Phase 4 continues for the lifetime of the project until the software is officially deprecated or reaches end-of-life (EOL).
